Reading the numbers: the prototype runs every tenant through one Python process with one lock, so it saturates once demand exceeds what a single core can process. Up to that point every request succeeds and nothing is lost; past it, latency grows rather than data being dropped, because collectors keep payloads in their outbox until acknowledged. The production path (stateless ingest behind a queue, AIOps workers sharded by series) removes the single-process ceiling; see ARCHITECTURE.md section 8.

## Mutual TLS did not change throughput

The previous version of this file showed 93.7 payloads/s at 100 collectors, measured before mutual TLS with
TLS 1.2+. The absolute ceiling on this laptop varies a lot with machine state, so the two versions were run
back to back on the same machine (same commands, `--collectors 25 100 --seconds 20`, alternating):

| Run | Before mutual TLS (`1bec683`) | With mutual TLS 1.3 |
|---|---|---|
| 1 | 25: 23.8/s, 100: 46.0/s | 25: 23.8/s, 100: 46.0/s |
| 2 | 25: 23.8/s, 100: 47.0/s | 25: 23.9/s, 100: 71.1/s |

Single 100-collector runs with mutual TLS switched off and on in the same code gave 79.6 / 92.1 and
91.8 / 92.6 payloads/s. The client-certificate handshake is not the bottleneck; the single SaaS process is.
